## Assembly and implementation security

I inspected the normal-build vector-dot-product function and Montgomery reducer for all three parameters. I also extracted the corresponding functions from retained EXP-001 timing binaries. Their source, compiler and flags match accepted evidence. The original baseline's vector-function instructions match EXP-001's after resolving code addresses; EXP-001's changed basemul callee is covered by its earlier review.

GCC 13.3.0 unrolls the new inner K-component loop. Signed coefficient loads extend to 32 bits, and products/accumulators remain 32-bit until reduction. Two conditional branches control the public pair counter: termination at 128 and odd/even parity. Coefficient/output addresses and zeta indices depend on public counters and fixed component offsets. Both parity paths execute three Montgomery reductions per pair; four static call sites reflect a duplicated first-call path, not four calls per iteration. The function ends with a direct tail jump to unchanged poly_reduce. The Montgomery reducer remains identical at 22 bytes. No division, indirect call or new secret-dependent branch/address was identified in these reviewed bodies.

|---|---:|---:|---:|
| Kyber512 | 132 -> 285 | 528 -> 24 | 552 -> 72 |

The last column excludes the entry return address and callees' stack use. These are local function observations, not whole-executable size or peak-stack measurements. The 512-byte temporary polynomial is gone, but the new function body is larger. Reduced calls, changed loop structure, memory use and code layout can all influence runtime.

A relevant hardening change is visible: EXP-001 has a local stack-canary check and a call to __stack_chk_fail; EXP-002 has neither in this function after replacing the local array with scalars, under the same compiler flags. No stack-protection flag was disabled. This changes local stack-corruption detection coverage and must not be presented as an unconditional security improvement. The fixed-index bounds and exercised checks support this implementation, but do not prove absence of memory errors or exploitability. Any measured speed difference includes this generated-code change; it cannot be attributed solely to Montgomery-call savings.

The range argument remains S00/S11 <= 27256320, S01 <= 54512640 and |t*zeta + S00| <= 32794112, under |a| <= 4095, |b| <= 1664, |zeta| <= 1664 and K <= 4. These fit int32_t and the reducer's input contract. The inner reduction preserves Montgomery scale, and final poly_reduce restores the expected centred representation. Existing signed-narrowing/shift assumptions remain. The current KEM callers use separate input/output objects; no general aliasing contract or arbitrary-int16-input guarantee is added.

I accept the scoped arithmetic/compatibility evidence and document the hardening tradeoff for research timing. Whole-program constant-time behaviour, statistical leakage, other compilers/targets, power/EM leakage and fault resistance remain unestablished or unassessed. An ordinary speed benchmark is not a leakage test or production security approval.
