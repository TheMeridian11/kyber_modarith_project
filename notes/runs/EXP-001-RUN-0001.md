## Verified results

All 42 build, test and disassembly steps completed with exit code zero. I checked 84 stdout/stderr hashes, 18 retained executable hashes, six support-file hashes, metadata, source files and their committed contents. The baseline matches the pinned upstream source. Only the candidate basemul body differs.

For each parameter set, all four transcripts (baseline/candidate, normal/UBSan) are byte-identical. Their sizes are 416000, 595200 and 806400 bytes for Kyber512, Kyber768 and Kyber1024 respectively. These cover 100 deterministic KEM fixtures per build, including successful exchanges, corrupted/random ciphertexts, malformed secret keys and noncanonical public keys. Agreement includes the tested rejection outputs, not only valid shared secrets.

All twelve builds passed 3200 kernel-oracle and output-bound checks each. The same cases are repeated across build variants; this is not 38400 independent input designs. The six UBSan builds produced no sanitizer diagnostics on the exercised paths. All builds were free of compiler diagnostics. Each candidate also passed the upstream suite of 1000 valid-exchange, 1000 replaced-secret-key and 1000 corrupted-ciphertext cases.

## Generated-code and implementation-safety findings

I inspected both variants' normal-build basemul for all three parameter sets, plus the Montgomery reducer extracted from the retained binaries. GCC 13.3.0 produced:

- Five direct reducer calls in the baseline and three in the candidate.
- Five product multiplications in both basemul bodies; fusion removes reductions, not those products.
- Two 32-bit accumulator additions before the candidate's final reductions, with narrowing only when outputs are stored.
- Fixed input/output offsets, direct calls and no conditional branches, divisions or indirect calls in either reviewed function.
- Basemul symbol sizes of 138 bytes versus 114 bytes; the reducer is unchanged at 22 bytes. These are function sizes, not complete executable sizes.
- The same four saved registers and eight additional stack-reservation bytes in both basemul prologues. There is no observed increase in this local stack setup; whole-program peak stack usage was not measured.

The reducer uses register arithmetic and a fixed shift. Its generated logical right shift preserves the returned low 16-bit result; it does not contradict the source's signed-shift semantics for that returned value. The existing GCC-specific narrowing assumptions remain.

The caller-bound argument still limits the largest fused accumulator to 13628160 and the sum of four outputs to 13312. Sampled oracle checks, byte compatibility and UBSan support that argument without proving every possible execution. No new branch/index-based leakage mechanism was found in the inspected bodies. Whole-program constant-time behaviour, statistical timing leakage, power/EM leakage and fault resistance remain unestablished or unassessed. The normal timing benchmark is not a leakage test.

## Decision

This validation run establishes no speedup. The subsequent [RUN-0002 timing review](EXP-001-RUN-0002.md) combines performance evidence with these scoped correctness/security findings.

I preserve every RUN-0001 file unchanged. Its manifest correctly records assembly_review as pending at execution; this later review resolves that action in a separate record. The subsequent timing runner checks that the actual timing binaries' reviewed functions match these instruction sequences, ignoring only code addresses and direct-call locations.
