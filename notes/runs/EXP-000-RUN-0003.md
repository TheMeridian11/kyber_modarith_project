## Observed durations

I report the median of the five process-level medians, converted from nanoseconds to microseconds.

| Parameter set | Key generation (microseconds) | Encapsulation (microseconds) | Decapsulation (microseconds) |
|---|---:|---:|---:|
| Kyber512 | 18.6885 | 21.2705 | 27.8050 |
| Kyber768 | 32.5920 | 34.7770 | 43.0455 |
| Kyber1024 | 49.5855 | 55.0405 | 64.8405 |

These measure the existing deterministic key-generation and encapsulation APIs plus valid-ciphertext decapsulation. Fixture generation and operating-system randomness are outside the measured operation intervals. The unit is elapsed time, not CPU cycles.

For each parameter/operation, I calculated 100 * (largest process median - smallest process median) / median of process medians. These descriptive ranges span 0.56% to 1.94%. They are neither confidence intervals nor a significance threshold. Individual large observations remain in the raw data; the largest was 406298 ns. The data do not identify their cause.

The environment was WSL2 on an i9-12900KS with GCC 13.3.0, using guest logical CPU 0. Host power mode, background load and physical-core placement were not established. I therefore treat these as pilot measurements in the recorded environment, not universal hardware performance or proof of repeatability across sessions.

## Sample volume and interpretation

I collected 3 parameter sets * 5 fresh processes * 1000 exchanges * 3 operations = 45000 timing rows. This represents 15000 complete measured exchanges. There are 1000 distinct fixture indices per parameter set, reused in each repetition; there are five process-level summaries for each parameter/operation, not 45000 independent experiments.

The sum of measured intervals is approximately 1.80 seconds, excluding warm-up, builds, fixture generation and other harness work. This amount of automated sampling is practical. The pinned upstream test/test_speed.c also defines NTESTS as 1000; that precedent does not itself establish statistical sufficiency.

I retain five processes of 1000 exchanges as the starting comparison budget. I will compare baseline and candidate in alternating matched blocks under the same recorded conditions. If a small effect remains uncertain, I will collect additional complete comparison blocks and retain all observations, rather than repeating only a favourable variant. No additional timing run is required merely to expand this pilot.

## Decision

I accept RUN-0003 as the initial timing baseline. No optimisation has been applied, so no speedup has been established. The next baseline record is reduction counting, EXP-000/RUN-0004. Candidate-specific bounds, byte-level compatibility, arithmetic checks and implementation timing review will accompany the first optimisation.
