## Generated code and hardening

I reviewed the normal candidate functions against fresh extractions from the accepted EXP-005 timing binaries. All 33 control/candidate extracts have sizes checked against nm. I also re-extracted all 33 saved baseline/candidate bodies from the validation binaries and verified their recorded normalised instructions; the overlapping original-baseline functions agree with earlier validation.

The general dot, poly_tomont and both reducers match EXP-005 exactly after relocation normalisation. After renaming self-branch symbols, each new keygen-dot body matches the general dot instruction-for-instruction except its final tail jump: poly_reduce becomes poly_tomont. It restores the local stack and saved registers before that jump. The wide accumulation remains int32 arithmetic; component operations are unrolled. Branches depend on public pair parity and fixed 128-pair termination; operand addresses and twiddle indices follow public positions. The unchanged poly_tomont executes 256 fixed-index Montgomery conversions with multiplier 1353. Both reducers retain fixed arithmetic without division or conditional branches.

|---|---:|---:|---:|---:|

The code-size sum is scoped to the changed keygen body and newly added dot body; it is not total executable size or a measured instruction-cache cost. Local stack includes saved registers and excludes the entry return address and callees; it is not peak KEM stack. Keygen reservations are 5224/9320/14984 bytes in EXP-006, plus 48 saved-register bytes each. Each new dot has a 24-byte reservation plus 48 saved-register bytes, matching the general dot's local footprint.

The keygen entry calls the new function instead of a general-dot call followed by poly_tomont. Kyber512 uses two direct calls, Kyber768 now unrolls its formerly looped three calls, and Kyber1024 retains the public four-row loop. Direct error NTT calls, skpv reduction, final addition/reduction and serialization remain. Kyber512/768 keygen bodies contain the canary conditional; Kyber1024 also retains public-matrix rejection sampling and public loops. I do not describe whole-keygen execution as branchless or independent of every public input.

Keygen canary loads/checks/failure calls, endbr64 and one/two/three stack-page probes remain. The general dot already lacks a local canary following EXP-002; EXP-006 preserves that function and adds a dedicated dot with the same hardening pattern. No protection flag is disabled. Instruction presence does not prove runtime CET enforcement or exhaustive memory safety. The added body and changed unrolling/call layout may influence performance alongside reduced Barrett calls, so a speed result will not isolate one reduction's cost.

## Security scope and subsequent timing

I observed no new secret-coefficient-dependent control/address choice in the reviewed changed path. This is bounded source/generated-code evidence, not whole-program constant-time proof. Correctness, invalid-input tests, explicit ranges and exercised UBSan checks support the implemented transformation within the stated contracts. Larger representatives change internal bit patterns; power/EM/fault effects, complete memory safety, portability and final ML-KEM conformance remain unestablished.

This validation run contains no dynamic secret-flow or statistical leakage measurements. The later [EXP-007 review](EXP-007-RUN-0001.md) directly tests EXP-006, while EXP-008 tests original/EXP-003/EXP-005. The [security summary](../final_security_summary.md) retains that distinction. VTune is outside scope.

Its development check passed six builds, 33 assembly matches and twelve short processes in both orders; these short checks supplied no thesis speed estimate. EXP-006 was the final arithmetic trial before security testing and the closing comparison.
